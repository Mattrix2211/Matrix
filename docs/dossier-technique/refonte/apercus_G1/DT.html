⟦dt-2-4⟧2.4 Ajouter une action de seuil

Un seuil est une entrée du registre central REGISTRE_ACTIONS (matrix/core/role_thresholds.py) : clé, libellé, catégorie, portée et niveau par défaut. Les seuils sont ensuite réglables par bâtiment.

  1. Ajouter une entrée ActionSeuil(clé, libellé, catégorie, PORTEE_NAVIRE, RoleLevel.…) au registre.
  2. Lire la valeur : seuil_role("<clé>") renvoie le niveau par défaut (constaté : 2 pour le niveau chef de section).
  3. Contrôler la cohérence : le registre passe de 35 à 36 actions ; la suite matrix.tests.test_coherence_configuration reste verte.
  4. Protéger l'écriture côté serveur avec niveau_requis_pour(user, clé) : le menu masque, c'est le serveur qui décide.

⟦dt-3-2⟧3.2 La relève : mécanisme exact

Tout le double équipage est dans matrix/core/equipage.py. Ce module est le seul à lire ou écrire Ship.equipage_a_bord : le reste du code passe par equipage_a_bord(navire) (:45), qui applique d'abord les relèves planifiées dont la date est atteinte.

Étape Fonction Contrôles
Proposition proposer_releve (:170) auteur commandant ou second d'un des deux équipages ; date non passée ; double équipage activé et équipage à bord renseigné ; l'équipage proposé n'est pas déjà à bord ; l'autre équipage a au moins un commandant ou second actif ; aucune relève ouverte ou planifiée. Notifie les commandants de l'autre équipage.
Décision decider_releve (:219) → _appliquer_decision (:318) relève encore en attente ; décideur commandant ou second de l'autre équipage ; pas l'auteur. Refus → refusee ; validation avec date future → planifiee ; sinon application immédiate.
Application _appliquer (:353) change equipage_a_bord, ferme la période ouverte à la date d'effet et ouvre la suivante (_enregistrer_periode), trace, génère la synthèse de passation. La relève reste appliquée même si la synthèse échoue (trace passation_echec).
Application planifiée appliquer_releves_echues (:66) idempotente, bâtiment verrouillé puis relève relue sous verrou ; appelée par la tâche planifiée appliquer_releves_echues_minute (toutes les 60 s) et à chaque lecture de l'équipage à bord.
Annulation annuler_releve (:422), annuler_releve_planifiee (:445) l'auteur annule sa proposition en attente ; une relève planifiée s'annule avec justification par un commandant d'un des deux équipages ; une relève appliquée ne s'annule pas.
Secours valider_releve_secours (:275) administrateur général seulement, motif obligatoire, seulement si l'équipage valideur n'a ni commandant ni second.

Concurrence. Le bâtiment est verrouillé (select_for_update) pendant proposition, décision, annulation et application ; la relève est relue sous verrou, ce qui rend une double validation inoffensive. L'unicité partielle SQL double ce contrôle.

⟦dt-3-4⟧3.4 Archivage et suppression des unités

Règle d'activité (org/archivage.py). est_active (:30) : une unité est active si elle et tous ses ancêtres ne sont pas archivés. verifier_modele (:106) est appelée par clean() de chaque modèle d'unité : elle refuse d'archiver une unité occupée (marins actifs, installations, matériel, sous-unités comprises), de réactiver sous un parent archivé, de créer ou déplacer sous un parent archivé. Un rattachement déjà porté reste tolérable ; une nouvelle affectation vers une unité archivée est refusée dans les formulaires, l'affectation en masse, l'import et l'API. Les listes de choix de nouvelles saisies (chef de liste, secteur d'une anomalie, cibles d'annonces, documents, programme, postes) ne proposent que les unités actives ; la lecture de l'existant est inchangée.

Règle de suppression (org/structure_services.py).

  • dependances(unite) (:35) parcourt l'unité et ses sous-unités, puis compte pour chaque relation entrante : les relations en PROTECT (via le gestionnaire de base) et les relations plusieurs-à-plusieurs. Les sous-unités et ReferenceBatiment.unite sont exclus (hiérarchie vide, simple référentiel).
  • verifier_suppression (:57) lève SuppressionRefusee avec le détail par type d'objet et trace la tentative (suppression_unite_refusee).
  • supprimer (:65) vérifie, supprime dans une transaction, et trace delete_<type> ; un ProtectedError tardif (objet rattaché entre le contrôle et la suppression) est converti en refus.
  • 92 relations vers les unités sont en PROTECT (inventaire de 105 relations dans 14 applications, Q §2) : Django refuse donc aussi toute suppression directe contournant le service. 14 migrations AlterField, sans SQL.
  • Interfaces : Réglages (refus avec détail, périmètre limité au bâtiment de l'appelant), API : code 409 avec détail au lieu de 204, administration Django (même service, y compris « supprimer la sélection »).

⟦dt-4-2⟧4.2 Deux familles de comparaison de seuils

Le seuil d'une action est un niveau. Il est comparé de deux manières selon l'endroit du code, et la différence ne concerne en pratique que le commandant en second et le soutien à terre.

  1. Comparaison au niveau d'écriture (niveau_ecriture) : API des ViewSets via RolePermission, et les vues qui l'utilisent. Le second est traité en équipier (sauf action marquée ouverte_au_second).
  2. Comparaison au grade (user_role_level) : la plupart des vues web de gestion (par exemple gestion des modules, matrix/views.py:289 ; saisie du programme, programme/services.py:47 ; fiches, assets/fiche_validation.py:130). Le second y atteint son grade.
  3. niveau_pour_action(user, clé) (matrix/core/role_thresholds.py) fait la synthèse pour les actions explicitement ouvertes au second.

Conséquence pour la lecture de l'annexe B : la colonne « Second » porte « ✱ » quand son grade atteint le seuil mais pas son niveau d'écriture ; l'accès réel dépend de la vue.

⟦dt-4-3⟧4.3 Le chemin d'une écriture par l'API

  1. Authentification : bloc REST_FRAMEWORK (matrix/settings.py:239) : SessionAuthentication puis BasicAuthentication. Permission par défaut : IsAuthenticated.
  2. Chaîne de middlewares (matrix/settings.py:115), dans l'ordre : contexte de configuration → sécurité Django → session → commun → CSRF → retrait du caractère NUL → authentification → déconnexion par inactivité → messages → clickjacking → identité de page → habillage des erreurs 400 → bâtiment courant → mot de passe provisoire → modules activables → lecture seule à terre → erreurs de saisie.
  3. RolePermission.has_permission (matrix/core/permissions.py:45) : lecture = authentifié ; superutilisateur = autorisé ; sinon niveau_ecriture(user) >= seuil. Le seuil vient de l'attribut du ViewSet role_threshold_action_write (et role_threshold_action_delete pour DELETE), clé du registre résolue au bâtiment de l'appelant ; à défaut, d'anciens attributs min_role_level_write/min_role_level_delete (constantes) puis CHEF_SECTION.
  4. has_object_permission (:52) : niveau_ecriture_sur(user, objet, strict=False) : l'état-major ramené au niveau équipier hors des services de sa fonction ; un assigné peut modifier sa propre occurrence de maintenance.
  5. Périmètre : le queryset du ViewSet est borné par build_scope_q ; une cible hors périmètre répond comme si elle n'existait pas.
  6. Trace dans AuditLog pour les actes sensibles.

Pour une vue web, les étapes 3 et 4 sont réalisées dans la vue (ou son services.py) avec niveau_requis_pour(user, clé), dans la plupart des cas ; le menu ne fait que masquer.

⟦dt-7-3⟧7.3 Mécanique des listes

  • Proposition : ListeServiceAbstract.proposer (quarts/models.py:488) passe au statut proposé, trace liste_service_proposee et notifie les publicateurs (niveau « Important », régime du type de liste).
  • Publication : publier (quarts/models.py:515) fige une Version… (creer_version, quarts/models.py:579), trace liste_service_publiee ; seule la première publication notifie chaque marin affecté.
  • Modification d'une liste publiée : tracer_modification_creneau trace et notifie le marin (niveau « Important », motif), rien pour un brouillon ou une proposition.
  • Publication à titre prévisionnel : publier_a_titre_previsionnel (quarts/activation.py:169) : statut proposé obligatoire, prise d'effet prévue obligatoire, application PREVISIONNELLE, réévaluation du bâtiment.
  • Activation : activer_liste (quarts/activation.py:205) verrouille la liste, vérifie l'habilitation, le statut (publiée + prévisionnelle), le mode du bâtiment (mode_du_batiment, quarts/mouvements.py:41 : dernier mouvement valide ; None = non renseigné → refus ; mer → refus), l'activation anticipée (seuil_activation_anticipee, quarts/activation.py:191), les conflits (conflits_activation, quarts/activation.py:134), puis passe en ACTIVE, ferme les alertes, trace, applique les échanges préparés, notifie les marins.
  • Mode du bâtiment : déduit des MouvementBatiment valides ; intervalles_par_mode (quarts/mouvements.py:55) découpe une plage par mode ; deux mouvements valides consécutifs ne mènent jamais au même mode ; un mode ne s'initialise qu'avant tout autre mouvement.
  • Alertes : quarts/alertes_activation.py (rappel, alerte, escalade, report et retrait motivés) ; tâche planifiée traiter_echeances_activation_minute (60 s).
  • Régularisation d'un quart : quarts/regularisation.py, à l'heure effective, motivée.

⟦dt-11-1⟧11.1 Vue d'ensemble du module

Le module est réparti sur trois paquets : maintenance (plans, échéances, exécutions, comptes rendus, tournée), logistics (tickets correctifs, anomalies, demandes de pièces) et assets (fiches, installations, mesures, qui alimentent l'exécution). Le module rondes est présent dans le dépôt mais sans aucune vue : ne pas le confondre avec une fonctionnalité.

Les trois objets du fonctionnel se retrouvent ainsi : l'occurrence (MaintenanceOccurrence), l'anomalie (Anomalie) et le ticket (CorrectiveTicket). L'ensemble s'exécute dans le processus web ; plusieurs tâches planifiées (génération des échéances, retard, notifications, détection de dérive : voir « Tâches planifiées et signaux ») dépendent de Celery et de Redis.

⟦dt-17-1⟧17.1 L'essentiel en un schéma

Matrix est une application web classique : un serveur qui fabrique des pages et répond à des demandes, une base de données qui garde l'information, et un service d'arrière-plan qui fait le travail planifié (rappels, alertes, application des relèves). Tout fonctionne sur le réseau du bord, sans Internet.

  • Les marins se connectent avec un navigateur (PC, tablette, mobile) au serveur du bord.
  • Le personnel à terre et l'équipage à terre utilisent le même serveur avec un périmètre réduit (DT §3 et DT §4). 🔵 Une architecture à serveurs distincts (bord et terre) avec synchronisation est un objectif de la phase 7, non développé : aujourd'hui, il y a un seul serveur.

⟦dt-17-4⟧17.4 Les couches et le trajet d'une requête

  1. Le navigateur envoie une requête (page ou API).
  2. Elle traverse la chaîne de middlewares (matrix/settings.py:115), qui pose le contexte (version de configuration, session, bâtiment courant) et refuse d'emblée ce qui ne doit pas passer : déconnexion par inactivité, mot de passe provisoire à changer, module désactivé, écriture d'un équipage à terre, page ouverte pour un autre marin. Le détail est au DT §21 (schéma S11).
  3. La vue (page ou API) vérifie le rôle, le seuil de l'action et le périmètre.
  4. Elle délègue à un service métier : validation, transaction, enchaînements vers les autres modules, trace dans le journal d'audit.
  5. Les modèles lisent et écrivent la base.
  6. La réponse est une page, un fragment HTML (HTMX met à jour une zone sans recharger la page) ou du JSON.

Le service d'arrière-plan (Celery) appelle les mêmes services métier ; il ouvre et ferme le même contexte de configuration que les requêtes web (matrix/celery.py).

⟦dt-18-3⟧18.3 Les conventions du code

  • Horodatage systématique. La plupart des modèles héritent de TimeStampedModel (matrix/core/models.py:4) : date de création et de dernière modification. Un second socle, OwnedModel, ajoute auteur et dernier modificateur.
  • Listes de choix en base, pas dans le code. Grades, spécialités, fonctions, types d'absence, domaines de RETEX, types de programme, catégories du catalogue sont des tables modifiables par un utilisateur habilité (principe « configuration plutôt que code »).
  • Configuration en champs JSON. Les réglages par bâtiment ou par secteur sont des champs JSON (seuils de rôle, préférences de secteur, widgets), avec repli sur une valeur par défaut tant que rien n'est réglé.
  • Statuts et journal de statut. Les objets à cycle de vie portent un champ de statut et, pour les plus sensibles, un journal dédié : OccurrenceStatusLog, TicketStatusLog, AnomalieStatutLog, EchangeServiceEvenement.
  • Versions pour « proposer, valider, publier ». VersionQuart, VersionServiceGarde, VersionFeuilleService, VersionAnnonce, VersionDocument conservent chaque version ; la version publiée reste active jusqu'à validation de la suivante.
  • Pas d'écrasement silencieux. Les modifications importantes écrivent une ligne dans AuditLog (acteur, action, cible, détails horodatés) ; un compte rendu corrigé conserve la saisie d'origine (ModificationCompteRendu).

⟦dt-18-4⟧18.4 L'intégrité : ce qui protège les données

Chaque relation dit ce qui doit arriver quand l'élément visé disparaît. Les trois règles employées, avec leur fréquence dans l'état B :

Règle Signification Nombre de relations
PROTECT La suppression de l'élément visé est refusée tant qu'il est référencé 115
SET_NULL Le lien est vidé (la relation devient facultative), l'enregistrement reste 216
CASCADE L'enregistrement qui référence est supprimé avec l'élément visé 102
Plusieurs-à-plusieurs Table de liaison 15

Lecture : par défaut, rien n'est supprimé en cascade sauf les éléments qui n'ont pas de sens seuls (une section sans secteur, une ligne de checklist sans sa liste, un message sans sa discussion). Les relations vers les unités sont en PROTECT depuis le lot L03 (92 relations, DT §3) : un marin, un matériel, une liste ne disparaît pas parce qu'on supprime une unité.

À connaître. Une relation générique (la section « Les relations génériques ») n'est pas vue par la base comme une relation : supprimer l'objet visé ne supprime pas, et ne refuse pas non plus, ce qui le désigne.

⟦dt-19-3⟧19.3 Authentification et contrôle d'accès

  • Authentification (réglage REST_FRAMEWORK) : session (celle du navigateur) et authentification HTTP « Basic ». Aucun jeton, aucune clé d'API, aucune délégation : un client automatique s'authentifie avec un compte nominatif.

  • Droit de lecture : toute personne authentifiée, bornée par le périmètre (ScopedQuerySetMixin, matrix/core/mixins.py:101) : bâtiment, service, secteur, section. Un modèle sans champ de périmètre direct refuse de répondre plutôt que de répondre sans filtre.
  • Droit d'écriture : classe RolePermission (matrix/core/permissions.py:9) : seuil de rôle par action, résolu selon la configuration du bâtiment de l'appelant ; un état-major n'écrit que sur les services rattachés à sa fonction ; un assigné peut modifier sa propre occurrence de maintenance.
  • Suppression protégée : supprimer une unité référencée renvoie 409 avec le détail et le nombre d'objets liés (SuppressionRefuseeAPI, org/views.py:38), jamais une suppression en cascade (lot L03).
  • Statut d'une occurrence : non modifiable par une écriture générique ; seules les actions dédiées (démarrer, terminer) le changent, avec la confirmation des installations critiques.
  • Modules désactivés : l'API continue de répondre même si le module est désactivé pour le bâtiment ; seules les pages web sont bloquées (vérifié par test le 12/11/2026 : lecture et écriture API, administration Django, tâches planifiées et enchaînements internes continuent ; l'accueil et le calendrier continuent aussi d'afficher les données du module). Ce choix évite de casser les enchaînements internes ; ◯ il doit être connu de tout intégrateur.

  • Format : JSON, avec suffixe de format (.json) accepté ; filtres, tri et recherche texte par les filtres standards (django-filter, OrderingFilter, SearchFilter).

Public : développeurs, administrateurs · Ce que vous y trouverez : les mécanismes par lesquels Matrix protège l'accès, les données et la traçabilité — décrits comme des **mécanismes**, pas comme une liste de défauts. ⟦dt-21-1⟧21.1 La démarche : plusieurs barrières successives

Matrix ne fait pas reposer la sécurité sur un seul contrôle. Une action d'écriture franchit plusieurs barrières, dont aucune n'est l'interface : l'écran masque des boutons, c'est le serveur qui décide.

⟦dt-21-3⟧21.3 Authentification et sessions

  • Connexion par identifiant et mot de passe (/accounts/login/). Les contrôles de mot de passe sont ceux de Django : longueur minimale, mot courant refusé, entièrement numérique refusé, trop proche de l'identité refusé (matrix/settings.py:210).
  • Création de compte sans mot de passe utilisable. L'administrateur du bâtiment réinitialise ensuite : mot de passe provisoire de 14 caractères, affiché une fois, jamais journalisé, à changer à la première connexion (DT §4).
  • Déconnexion automatique après 900 secondes d'inactivité par défaut, bornée entre 60 secondes et 8 heures, avec avertissement ; les requêtes automatiques ne comptent pas (matrix/core/inactivite.py). Les brouillons sont enregistrés avant déconnexion.
  • Cookies de session et CSRF en mode « sécurisé » et redirection vers HTTPS hors DEBUG (matrix/settings.py:422-424). En développement local, HTTP simple reste possible.
  • API : authentification par session et, en plus, par BasicAuthentication (bloc REST_FRAMEWORK, matrix/settings.py:239) ; l'accès à l'API reste soumis aux mêmes permissions que les pages, sauf l'activation des modules : un module désactivé pour un bâtiment ne bloque que les pages web, jamais l'API (DT §19, écart A25).
  • Connexions et déconnexions sont tracées (accounts/signals.py).

⟦dt-21-4⟧21.4 Les fichiers téléversés

Les fichiers (photos de matériel, documents, pièces jointes, certificats…) ne sont jamais servis directement par le serveur web.

  • Toute adresse /media/… passe par servir_media (matrix/urls.py), qui consulte un registre : FichierProtege (matrix/core/medias.py:25) associe chaque dossier de dépôt à son modèle, son champ et la règle de consultation de l'objet qui porte le fichier (périmètre du matériel, de l'installation, de la tâche, de l'anomalie, dossier de formation visible…).
  • Un chemin absent du registre ou dont l'objet est hors périmètre répond 404, sans indice sur l'existence du fichier.
  • Quelques ressources communes à toute la flotte (silhouettes, photos du catalogue, barèmes) sont déclarées « tout utilisateur connecté ».
  • En production, MEDIA_ACCEL_REDIRECT permet de déléguer l'envoi au serveur web après autorisation (le fichier est livré par le serveur web, la décision reste à Django).
  • À l'envoi, matrix/core/validators.py contrôle l'extension autorisée, la taille maximale (DOCUMENT_TAILLE_MAX_MO, 20 Mo par défaut) et, pour les images, que le contenu est réellement décodable (on ne se fie ni au nom ni au type déclaré par le navigateur).

⟦dt-21-5⟧21.5 Le journal d'audit

accounts.AuditLog (accounts/models.py:177) enregistre : qui (acteur), quoi (action), sur qui (utilisateur cible), détails (texte), quand (horodatage). Il est alimenté par une vingtaine de modules du code.

Familles d'actions tracées (extraits) : comptes (create_user, edit_user, delete_user, changement_role, reinitialisation_mot_de_passe, bulk_*, connexion, déconnexion) ; équipage (releve_*, changement_equipage, fuseau_horaire_modifie) ; unités (suppression_unite_refusee, delete_<type>, archivage) ; quarts (liste_service_*, feuille_service_*, échanges) ; maintenance (correctif_compte_rendu*, occurrence_status_change, create_ticket*) ; formations, annonces, documents, programme, postes.

À connaître :

  • Les refus sont aussi tracés pour les actions sensibles (par exemple quarts/refus.py : activation, mouvements, régularisation, remplacement, réglages ; suppression d'unité refusée).
  • La confirmation explicite des validations critiques (clôture d'une maintenance critique, remise en service, clôture de la préparation à l'appareillage) est enregistrée avec le texte confirmé, sa version et le canal (web ou API) : matrix/core/confirmations.py. Ce n'est pas une signature électronique : la personne est déjà authentifiée, la trace atteste qu'elle a validé en connaissance de cause.
  • Un compte rendu corrigé conserve la saisie d'origine ; chaque version d'une liste, d'une feuille de service, d'une annonce ou d'un document est conservée.
  • ◯ Le journal est une table ordinaire de la base : il n'est pas scellé contre une modification par quelqu'un qui aurait un accès direct à la base. Sa durée de conservation n'est pas définie (information manquante IM-10 du dossier V1.2).

⟦dt-21-6⟧21.6 Proposer, valider, publier

Le principe 7 (RF §3) se retrouve dans le code sous trois formes :

  1. Versions : une modification d'une liste, d'une feuille, d'une annonce ou d'un document crée une version ; la publiée reste active jusqu'à validation.
  2. Circuits à deux acteurs : la relève d'équipage (un commandant propose, l'autre équipage valide), les échanges de tours, les fiches et articles du catalogue.
  3. Confirmation explicite pour les validations critiques (la section « Le journal d'audit »).

Aucune modification d'un objet validé n'écrase silencieusement l'ancien état.

⟦dt-22-5⟧22.5 Fonctionnement sur le réseau local du bord

🟢 Principe du projet : « Internet n'existe pas ». Polices, icônes, graphiques, calendrier et scripts sont embarqués ; aucun CDN, aucune API distante, aucune télémétrie. L'application sert un réseau fermé.

  • Clients : navigateurs des postes fixes du réseau du bâtiment (et de l'intranet à terre) ; aucun client lourd.
  • Hôtes acceptés : DJANGO_ALLOWED_HOSTS doit contenir le nom ou l'adresse sous lesquels les postes joignent le serveur.
  • Base et file : joignables depuis la machine du serveur seulement (liaison 127.0.0.1), pour ne pas exposer la base au LAN du bord (commentaire du fichier docker compose).
  • HTTPS : en production, SESSION_COOKIE_SECURE, CSRF_COOKIE_SECURE et SECURE_SSL_REDIRECT sont actifs : toute requête HTTP est redirigée vers HTTPS, les cookies ne circulent qu'en HTTPS. Aucun certificat ni serveur HTTPS n'est fourni : à fournir avec les SIC.
  • ◯ Non trouvés dans le code : réglage d'un proxy inverse (SECURE_PROXY_SSL_HEADER), HSTS, configuration de journalisation (LOGGING), limitation des tentatives de connexion. Les origines CSRF de confiance sont codées en dur sur localhost/127.0.0.1:8000 : à revoir selon l'architecture réelle (nom d'hôte, proxy).
  • Web Push : exige HTTPS ou localhost côté navigateur ; dégradé proprement sans (les notifications dans l'application continuent).
  • E-mail : par défaut en console ; un relais SMTP à bord est à fournir si l'on veut des messages.
  • Synchronisation bord–terre : inexistante ; chaque instance est autonome (cible, RF §21).
  • Fichiers téléversés : stockés sur le disque du serveur ; servis par l'application après contrôle des droits.

⟦dt-25-1⟧25.1 Pourquoi des annexes hors du PDF

Les inventaires détaillés (routes, modèles, variables, matrice de couverture, éléments non vérifiés) sont consultés par recherche et par tri, pas lus de bout en bout : ils sont fournis sous forme d'un fichier HTML autonome et de fichiers CSV (UTF-8, séparateur « ; »), dans le dossier des annexes consultables. Le fichier HTML ne demande aucune connexion et aucune police distante ; chaque fichier porte la mention provisoire. Le PDF ne garde que les totaux, la méthode et les extraits ci-dessous.

  1. L'inventaire du code de l'état B est généré par script (modèles, routes, tâches, commandes, actions, modules, signaux, dépendances).
