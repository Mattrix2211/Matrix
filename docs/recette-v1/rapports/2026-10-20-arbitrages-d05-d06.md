## 1. D-06 — Les 9 questions

Périmètre V1 proposé (tous en avertissement) : C1 même marin sur deux créneaux qui se chevauchent ; C2 créneau pendant une absence (« conflit » si validée, « à vérifier » si déclarée) ; C3 créneau hors de la période de la liste ; C4 deux listes de même type, périmètre, fonction et équipage aux périodes qui se chevauchent ; C5 habilitation manquante sur une garde (conditionnel, question 6).

### D6-Q1 — Avertissement seul ou blocage pour certains conflits ?
- **Aujourd'hui** : aucun contrôle à la saisie d'un créneau, à la proposition ni à la publication. Seuls les échanges de quarts détectent absences, chevauchements et habilitations, et ils bloquent.
- **Options** : (a) avertissement seul partout ; (b) blocage de certains cas (ex. absence validée) ; (c) avertissement par défaut, blocage configurable plus tard.
- **Recommandation** : (a). C'est l'orientation que vous avez confirmée. Le blocage suppose des exceptions (urgence, besoin du service) qu'on ne peut pas deviner.
- **Conséquences** : (a) aucune migration, 2 tâches ; (b) ajoute la tâche C (règles configurables, migration probable, +1 tâche grosse) et un risque de bloquer le chef un jour d'urgence ; (c) ajoute la même tâche C. Utilisateurs : (a) le chef garde la main mais peut ignorer l'avertissement ; (b) plus sûr mais plus rigide.

### D6-Q2 — Absence seulement déclarée (non validée) : la signaler ?
- **Aujourd'hui** : les échanges distinguent déjà « conflit » (absence validée) et « à vérifier » (déclarée).
- **Options** : (a) signaler comme « à vérifier » ; (b) ignorer ; (c) traiter comme conflit.
- **Recommandation** : (a), même distinction que les échanges (cohérence, un seul vocabulaire).
- **Conséquences** : (a) le chef voit tout, avec une gravité plus faible ; (b) risque de rater une permission en cours de validation ; (c) trop de faux conflits. Complexité identique.

### D6-Q3 — Quelles indisponibilités compter ?
- **Aujourd'hui** : le seul modèle d'indisponibilité est `Absence` (types configurables, jours entiers). Il n'existe ni inaptitude médicale, ni repos après un quart de nuit. Les sessions de formation n'ont pas de fin, donc aucune plage exploitable.
- **Options** : (a) tous les types d'absence existants ; (b) un sous-ensemble (ex. exclure le télétravail) via un réglage par type ; (c) créer de nouvelles sources.
- **Recommandation** : (a) en V1. Le sous-ensemble relève de la configuration des types d'absence, déjà modifiable sans code.
- **Conséquences** : (a) simple, un seul détecteur ; (b) un indicateur « bloque le planning » par type d'absence (migration) ; (c) hors V1, nouvelles données à saisir, nouveaux modèles. Recette : (a) sans impact.

### D6-Q4 — Quart et garde simultanés pour un même marin : parfois voulu ?
- **Aujourd'hui** : rien n'est détecté à la saisie ; les échanges signalent le chevauchement.
- **Options** : (a) simple avertissement que le chef peut ignorer ; (b) case « double poste voulu » par créneau.
- **Recommandation** : (a). Vous avez demandé de ne pas inventer de contrainte sur les doubles postes.
- **Conséquences** : (a) aucune migration ; l'avertissement peut rester affiché sur un double poste volontaire (bruit) ; (b) champ en plus, migration, +1 tâche, écran de plus, mais supprime le bruit.

### D6-Q5 — Publier malgré un conflit : justification ou simple trace ?
- **Aujourd'hui** : la publication ne contrôle rien et n'exige aucune justification.
- **Options** : (a) trace seule dans l'audit (nombre de conflits restants) ; (b) justification obligatoire ; (c) confirmation en deux étapes.
- **Recommandation** : (a). La justification obligatoire est déjà prévue pour l'urgence (D-05) ; l'exiger ici ralentirait la publication courante.
- **Conséquences** : (a) simple, aucune migration ; (b) champ de justification, texte à conserver, un clic de plus ; (c) écran de plus. Recette : (a) un scénario de moins.

### D6-Q6 — Qualifications : signaler l'habilitation manquante ?
- **Aujourd'hui** : une garde peut déjà porter des formations requises (`formations_requises`), contrôlées par les échanges. Les quarts n'ont aucune formation requise.
- **Options** : (a) signaler l'habilitation manquante sur les gardes uniquement (C5) ; (b) ne rien signaler ; (c) ajouter des formations requises aux quarts.
- **Recommandation** : (a). Cela réutilise une règle déjà configurée par le chef, sans en inventer. Vous avez demandé de ne pas inventer de contraintes de qualification : à **confirmer** que C5 sur les gardes ne contredit pas cette consigne. (c) est hors V1.
- **Conséquences** : (a) quelques tests de plus, pas de migration ; (b) divergence avec les échanges (un échange refusé alors que la saisie initiale passe) ; (c) nouveau champ de configuration, migration, cadrage métier.

### D6-Q7 — Repos minimal entre deux affectations
- **Aujourd'hui** : aucune notion de repos.
- **Options** : (a) hors V1 ; (b) paramètre de liste (durée en heures) ; (c) paramètre du navire.
- **Recommandation** : (a). Vous avez demandé de ne pas inventer de contrainte sur le repos : il faudrait une durée validée par la Marine.
- **Conséquences** : (a) rien ; (b) et (c) un paramètre (migration), des cas limites (changement de jour, nuit) et la tâche C.

### D6-Q8 — Comparer avec quelles listes ?
- **Aujourd'hui** : `conflits_marin` ne regarde que les listes publiées, donc une saisie en brouillon n'est jamais comparée.
- **Options** : (a) listes publiées + la liste en cours ; (b) toutes les listes, brouillons et proposées comprises.
- **Recommandation** : (a). Les brouillons d'autres chefs sont des intentions, pas des affectations : ils créeraient des faux conflits.
- **Conséquences** : (a) clair, peu de requêtes ; (b) bruit, risque de lecture de listes hors périmètre du chef, requêtes plus lourdes.

### D6-Q9 — Vue transverse « conflits à venir » pour le chef de service
- **Aujourd'hui** : le cas M08 a nécessité de croiser trois écrans à la main.
- **Options** : (a) non, le panneau de chaque liste suffit en V1 ; (b) une vue transverse du service.
- **Recommandation** : (a). Le panneau de liste et l'avertissement à la saisie couvrent le besoin immédiat. La vue transverse est différable.
- **Conséquences** : (a) rien de plus ; (b) +1 tâche grosse (périmètres, performance, nouvel écran), recette de plus.

## 2. D-05 évolutions — Les 10 questions

**Les quatre décisions bloquantes sont D5-Q1, D5-Q2, D5-Q4 et D5-Q5** : elles conditionnent la conception de la tâche A (proposition). Les six autres peuvent être tranchées en cours de route, avec la recommandation par défaut.

Principe de la conception proposée : une liste publiée reste active et inchangée tant que la nouvelle version n'est pas publiée. Une « proposition » (copie de travail) est préparée par le chef de liste, comparée et publiée par un utilisateur habilité, ou renvoyée avec motif. L'urgence applique la même copie sans étape de validation, avec justification et audit.

### D5-Q1 — BLOQUANTE : qui est « spécifiquement habilité » pour l'urgence ?
- **Aujourd'hui** : la publication est réservée par un seuil configurable (`liste_service_publication`, défaut CHEF_SERVICE) et un périmètre ; le commandant en second n'agit pas. Aucune habilitation d'urgence n'existe. Depuis D-05 technique, le chef de liste peut modifier directement, avec trace.
- **Options** : (a) un seuil réglable par l'administrateur de navire, défaut COMMANDANT (ou COMAEQ / chef de service selon la pratique du bord) ; (b) délégation nominative sur le modèle de `DelegationProgramme`.
- **Recommandation** : (a). C'est l'extension d'un mécanisme existant (le registre des seuils accepte une nouvelle action sans migration). (b) seulement si la Marine veut désigner une personne précise indépendamment du grade.
- **Conséquences** : (a) aucune migration pour les droits, réglable par navire dans Réglages › Sécurité ; (b) un modèle et des écrans de plus, migration. Recette : droits à tester par rôle, périmètre et double équipage dans les deux cas.

### D5-Q2 — BLOQUANTE : durée de vie d'une proposition non publiée
- **Aujourd'hui** : la notion de proposition d'une liste publiée n'existe pas.
- **Options** : (a) aucune expiration, mais « obsolète » si la liste change (échange validé, urgence) ou si la période est terminée, avec l'ancienneté affichée ; (b) expiration automatique après N jours ; (c) pas de gestion d'obsolescence.
- **Recommandation** : (a). Une expiration silencieuse ferait perdre un travail ; la règle d'obsolescence évite de publier sur une base périmée.
- **Conséquences** : (a) un contrôle à la publication (numéro de version de base), un message clair ; (b) tâche planifiée et durée à fixer par la Marine ; (c) risque de publier des créneaux déjà dépassés ou des échanges écrasés.

### D5-Q3 — Qui peut annuler une proposition ?
- **Options** : (a) son auteur, les chefs de la liste et les publicateurs, avec motif obligatoire et trace ; (b) l'auteur seul ; (c) publicateurs seuls.
- **Recommandation** : (a). Le publicateur peut aussi renvoyer au chef avec motif, comme pour la feuille de service.
- **Conséquences** : (a) cohérent avec les droits existants, un champ de motif ; (b) bloque si l'auteur est absent ; (c) le chef ne peut pas corriger son erreur. Complexité faible.

### D5-Q4 — BLOQUANTE : que voit le marin entre proposition et publication ?
- **Aujourd'hui** : rien, puisque la proposition n'existe pas ; les créneaux modifiés directement sont visibles aussitôt par le marin (c'est le défaut actuel).
- **Options** : (a) rien (ni calendrier, ni « Aujourd'hui », ni notification) ; (b) une mention « modification à l'étude » ; (c) une notification de préavis.
- **Recommandation** : (a). C'est votre exigence : une proposition ne doit pas faire croire que l'affectation officielle a changé. (b) et (c) risquent le faux signal.
- **Conséquences** : (a) aucun changement de code pour le calendrier (il ne lit déjà que les listes publiées), tests de non-régression ; (b) nouvel affichage et règle de gestion du signal ; (c) notifications à annuler si la proposition est abandonnée.

### D5-Q5 — BLOQUANTE : notifications (destinataires, Web Push, justification)
- **Aujourd'hui** : notification dans Matrix uniquement à la première publication ; le Web Push ne part que pour le niveau « danger ». Une republication ne notifie personne.
- **Sous-questions** : (a) destinataires ; (b) Web Push pour l'urgence ; (c) le marin voit-il la justification d'une urgence ?
- **Recommandation** :
  - (a) les marins touchés (ancien et nouveau titulaire) et les chefs de liste, jamais toute la liste, avec le détail de ce qui change et un lien vers la version à jour ;
  - (b) notification dans Matrix partout ; Web Push seulement pour l'urgence si le créneau commence dans les 24 h (seuil configurable), à confirmer. Dans tous les cas la notification reste accessible dans Matrix indépendamment du Web Push ;
  - (c) non : justification visible des gestionnaires et du commandement ; le marin voit « modification urgente », la date et l'auteur.
- **Conséquences** : une notification par marin touché et rien en cas de diff vide (comme vous l'avez décidé). Le Web Push dépend du réseau du bord (délai maximal désormais borné). Montrer la justification au marin peut exposer des motifs sensibles.

### D5-Q6 — Le chef de liste est-il notifié d'une urgence ?
- **Recommandation** : oui, pour qu'il ne planifie pas sur une base périmée.
- **Conséquences** : une notification de plus par urgence, aucune complexité.

### D5-Q7 — Créneaux déjà commencés ou passés : modifiables ?
- **Aujourd'hui** : rien ne l'empêche.
- **Options** : (a) non via la proposition, oui via l'urgence avec justification (correction a posteriori tracée) ; (b) jamais ; (c) toujours.
- **Recommandation** : (a).
- **Conséquences** : (a) un contrôle de date à la publication et une exception d'urgence ; (b) empêche de corriger une erreur ; (c) permet de réécrire l'historique d'un quart passé. Recette : cas limites de date et fuseau.

### D5-Q8 — Administration Django : créneaux d'une liste publiée en lecture seule ?
- **Aujourd'hui** : les formulaires intégrés de l'administration permettent de modifier ou supprimer sans circuit. D-05 technique ne trace que les ajouts et suppressions faits depuis l'administration.
- **Options** : (a) lecture seule sur liste publiée, avec exception MASTER_ADMIN tracée ; (b) laisser tel quel ; (c) fermer entièrement.
- **Recommandation** : (a).
- **Conséquences** : (a) ferme le dernier contournement du circuit (et règle le point de dette « modification non tracée », voir §5) ; (b) le principe « proposer → valider → publier » reste contournable ; (c) bloque une correction de dernier recours.

### D5-Q9 — Échange validé pendant une proposition
- **Aujourd'hui** : un échange validé modifie les créneaux et crée une version, ce qui est une modification effective légitime.
- **Options** : (a) bloquer la publication de la proposition (« liste modifiée depuis »), le chef actualise ou abandonne ; (b) reporter automatiquement l'échange dans la copie de travail.
- **Recommandation** : (a) en V1.
- **Conséquences** : (a) simple et sûr, un aller-retour manuel ; (b) fusion automatique avec cas limites (échange portant sur un créneau déjà modifié), risque d'erreur silencieuse, +1 passe de développement.

### D5-Q10 — Premier cas d'usage de la recette
- **Options** : (a) service de garde de 24 h (avec échanges) ; (b) quart.
- **Recommandation** : (a), le cas qui concentre le plus de règles (échanges, habilitations).
- **Conséquences** : (a) recette plus exigeante mais couvre aussi les quarts ; (b) recette plus rapide mais des cas non couverts.

Attention : cette voie n'impose pas de justification, ce qui est moins que votre exigence. On peut ajouter une justification obligatoire à cette voie provisoire (petite tâche) ou accepter l'écart jusqu'à la livraison de C.

## 5. Dette « modification d'un créneau non tracée » et périmètre de D-05 technique

- **Périmètre exact de D-05 technique (cc4ebff)** : tracer (historique + notification) l'**ajout** et la **suppression** d'un créneau d'une liste publiée, depuis la vue web et les formulaires intégrés de l'administration, pour les quarts et les gardes, de façon atomique. Il n'y a pas d'autre critère.
- **Fait vérifié dans le code** : la vue web n'offre **aucune action « modifier un créneau »** ; elle ne propose que `ajouter_creneau` et `supprimer_creneau`. Changer le marin ou l'horaire d'un créneau par la vue revient donc à supprimer puis ajouter, ce qui produit deux traces. Aucune modification silencieuse par la vue.
- **Le seul chemin de modification sans trace** est l'édition directe d'un créneau existant dans les formulaires intégrés de l'administration Django (le code de trace ne traite que les objets ajoutés ou supprimés, pas les objets modifiés).
- **Conclusion** : ce n'est pas un défaut de D-05 technique ; c'est hors de ses critères d'acceptation et le relecteur l'a confirmé. Le point sera résolu soit par la lecture seule de l'administration (D5-Q8), soit par la tâche A de D-05 évolutions. Il reste inscrit dans « Dette — quarts ». Un risque résiduel existe d'ici là : un administrateur peut modifier le marin ou l'horaire d'un créneau publié sans trace. Si cela vous préoccupe pour la recette, une petite tâche peut tracer aussi les créneaux modifiés dans l'administration (environ 2 passes).
